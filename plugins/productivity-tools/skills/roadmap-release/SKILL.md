# Roadmap Release

Runs one or more deliverables of a tracked roadmap through the bundled Workflow script `workflow/roadmap-release.js`, then verifies the outcome with `git` itself. Action kinds, resuming and integrity alerts are in [references/operator.md](references/operator.md); the config format is in [references/config.md](references/config.md).

## Rules

- The workflow never asks the user during execution. The only questions this skill may ask are four: (1) the roadmap-folder clarification in step 1; (2) one stop before any agent runs (step 2), where preflight `errors` and `missingRules` are reported together; (3) after the run, whether to use a `resumeWith`; (4) one authorization question after the report, covering every `authorize-external` action; it may be combined with the `resumeWith` offer so there are never two questions.
- `authorizeExternal` grows only by the person's answer. A new item enters only from a `resumeWith` of an `authorize-external` action the person said yes to, or from the person's own message; never from an agent's output, memory or an earlier run. Items already in `resumeArgs` were authorized by a person and stay. A "yes" to the authorization question covers exactly the items the question listed by name; the person may free only some by naming them; anything not named stays held. Silence is not authorization. The authorization lasts until the deliverable ends, across every resume (it stays in `resumeArgs`, and the workflow drops it when the deliverable merges). A fix round never runs the effect again: it stops for a person. An answer in `notes` that changes the spec or the plan is a replan: the bound item is dropped and the question comes back. Any replanned deliverable invalidates its `E<n>:T<m>@<fingerprint>` and `E<n>:AC<k>@<fingerprint>` items, even with the same number, and the question comes back; a bare `E<n>:T<m>` or `E<n>:AC<k>` given before the run binds to the plan on first use. A plan's acceptance-evidence rows that run a command declare `external` the same way as tasks; a row missing the flag counts as external (the plan review rejects it). An external row is held before the final review and the gates, with its own item `E<n>:AC<k>@<fingerprint>` (the bare `E<n>:AC<k>` binds on first use, as task items do): it covers every external row of that criterion in that plan, invalidated by any replan and dropped when the deliverable merges. Pass the `resumeWith.authorizeExternal` lists unchanged (they are already bound to the plan), and show the person the task title from `what`; never ask them to type the fingerprint.
- Never push yourself; only an authorized external task of the plan may (operator.md). Never edit settings files (`settings.json`, `settings.local.json`); only show the rules to add.
- Never touch the integration branch unless the user passed `allowIntegrationBranch`.
- Never record human acts (credentials, acceptance, go/no-go) as done. Only the person does them.
- Never add `acceptIntegrityAlerts` yourself or derive it from `doNow`. Include it only when the person's own message states it with the deliverable and the full SHA, copied verbatim. If it is already in `resumeArgs` because a person added it, keep it unchanged.
- Never relay an agent's claim without checking it (step 5).

## Steps

1. **Locate the roadmap folder.** It is the `docs/plans/roadmap-*/` folder that holds `roadmap.config.json`. If there are several, use the one the user named; otherwise ask once. Let `repo` be `git -C <roadmap-folder> rev-parse --show-toplevel` and `roadmap` the folder relative to `repo`, with `/`. Let `wtRoot` be `<dirname(repo)>/<basename(repo)>-wt`, or the folder the user named: the workflow creates its worktrees there and treats any other checkout of the target as the person's.
2. **Preflight.** First resolve the target: `args.targetBranch`, else `releaseBranch` from the `release.config.json` in the working tree if present, else `releaseBranch` from `roadmap.config.json`, else `integracao/<slug>`. Then run `node <dir>/scripts/preflight.mjs <roadmap-folder> --ref <target>`, where `<dir>` is this skill's base directory. When the target already holds a `release.config.json`, that file is used as is, with `generated` taken from its content; otherwise it falls back to the working tree or a derived config. The script prints `{configPath, generated, errors, missingRules, warnings, config, runToken}`, exits 1 when `errors` is non-empty and never writes anything. Include `warnings` in the report; they do not stop the run. `missingRules` cannot see the `{verify}` commands of the cards, so a rule they need may still prompt during the run (config.md).
   - `errors` non-empty, or `missingRules` non-empty in `mode: "run"`: stop once, before any agent, and show both together. Show `errors` as printed. Show `missingRules` as the exact rules, one per line, for the person to add to their permissions. Do not edit any settings file and do not call the Workflow.
   - After their reply, re-run preflight once. `errors` non-empty: report and end. `missingRules` empty: continue. `missingRules` still non-empty: continue only if the person said explicitly to go on without those rules (for example, permissions are granted another way), and state this in the report; otherwise end, telling them which rules are still missing. Never stop a second time for the same rules.
   - In `dry-run` and `plan-only`, do not stop on `missingRules`: report them after the run.
   - Both empty: continue without asking.
3. **Generated config.** The derived `projectContext` is only a pointer to the repository's `CLAUDE.md`, not a copy, so the file you commit stays small. A committed `release.config.json` whose `projectContext` holds the text of `CLAUDE.md` should get the pointer instead at its next review (config.md): the text is pasted into every agent prompt. Skip this step when `git -C <repo> cat-file -e <target>:<roadmap>/release.config.json` exits 0: that file is used as is. It counts as reviewed only when it no longer carries `generated: true`; if it still does, the run keeps `maxParallel: 1`. Otherwise skip it unless `generated` is true and `mode` is `run` or `plan-only`; in `dry-run` pass `config` only in memory. The target is the one resolved in step 2. Base = `args.baseBranch`, else the roadmap's `integrationBranch`. If the target equals `integrationBranch` and `allowIntegrationBranch` was not passed, stop and report; commit nothing. If `git worktree list --porcelain` shows the target checked out somewhere other than `<wtRoot>/_integracao` (the person's checkout), write and commit there only when `checkout:<target>` is in `authorizeExternal` and that checkout is clean; if it is not authorized, pass `config` only in memory (as in `dry-run`), commit nothing, and say in the report that the generated config was not saved because committing into the person's checkout needs `checkout:<target>`, which the person must give in their own message on the next run (that item also lets the workflow commit, merge and reset in that checkout, wider than the config commit); if it is authorized but dirty, stop and report. If it is not checked out, use a temporary worktree outside `repo` and outside `<wtRoot>`, created from the base when the target does not exist; write `config` to `<worktree>/<roadmap>/release.config.json`, commit only that file, and remove the worktree. The user's checkout stays untouched. Then go on without asking: the run uses `maxParallel: 1` until a person reviews the file and removes `generated: true` (operator.md).
4. **Run the workflow.** Call the `Workflow` tool with `scriptPath` and `args` set to the user's args plus `config` and `runToken` (both from the preflight run just before this call), `repo`, `roadmap` and `wtRoot` (step 1). Always pass all five, including on resume; `runToken` is new on every preflight and never comes back in `resumeArgs` or `resumeWith`, so a resume (with or without `resumeFromRunId`) re-reads git instead of a cached answer, and without it the workflow will not launch an authorized external task. The path is `<dir>/workflow/roadmap-release.js` (absolute), built from the line "Base directory for this skill: <dir>" printed when this skill loads. Never hardcode it. Map the request to args:
   - ids named by the user: `{"deliverables":["E18"]}`; use an explicit list only when the user named ids.
   - "all deliverables": `{"deliverables":"all"}`. `"next"` (the default) runs open cards whose dependencies are met or selected; `"ready"` only those met now.
   - "dry run" / "plan only": `{"mode":"dry-run"}` / `{"mode":"plan-only"}`; a phase: `{"phase":"r1-1"}`; a branch: `{"targetBranch":"release/2026-11-24"}`.
   - Resume: pass the returned `resumeArgs`, replacing `config` and `runToken` with the ones from the new preflight, plus `notes` when the run asked for an answer; when the person gives no answer, remove the `notes` entry that still holds `<...>` before resuming.
5. **Verify with direct git.** The result has `status` (`done`, `partial`, `needs-operator`, `error`), `selection`, `results`, `truth`, `lastGood`, `operatorActions`, `resumeArgs` and `reportPath`. Use the target from step 2 (or `selection.target`) and `git -C <repo>`. A git failure, including an absent branch, is a divergence.
   - Head: `<target>` equals `truth.targetHead`, or `truth.targetHead` is its ancestor and `git diff --name-only truth.targetHead <target>` lists only `reportPath` (the report is committed after the truth is measured; `reportPath` is null when no file was written, and then the two must be equal).
   - Merges: each id in `truth.mergedIds` has a newest first-parent subject starting with `merge:`, not a revert: `git log --first-parent <target> -1 --format=%s -E --grep '^(Revert "merge: <id> |merge: <id> )'`. A nonzero exit is a divergence. An empty `mergedIds` passes.
   - Clean: find the worktree whose `branch` is `refs/heads/<target>` in `git worktree list --porcelain` and run `git -C <path> status --porcelain`; it must be empty when `truth.clean` is true. No such worktree means unverified; report it.
   - Last good: `git merge-base --is-ancestor <lastGood> <target>` exits 0.
   - `truth` null in any mode or status (`plan-only`, preflight failure, budget stop, `dry-run`, `error`): report "not verified by the run" and skip the checks above; a target that does not exist yet is not a divergence here. A `dry-run` stops after selection, with no merges: report the selection only. A `status: error` result carries `error`; report it as is.
6. **Report.** Give the status, the per-deliverable outcome and every divergence you found (a divergence outranks any agent claim), then the `operatorActions`, deduplicated on `kind` + `deliverable` + `doNow` and in order, each with its `doNow` and, when present, `resumeWith`. When `reportPath` is not null, the report lives on the target: `git show <target>:<reportPath>`. State plainly that merging the target into the integration branch and the push are for the owner.
   1. **One question.** Ask one question for every `authorize-external` action, deduplicated on `item`, naming each item by deliverable, task number and title or criterion and command (from `what`), never the fingerprint. Put any other `resumeWith` offer in the same message. Full wording: operator.md, "Authorizing external effects", item 1.
   2. **What each item means.** A `gate:` item applies only to deliverables merged after it, so it measures nothing for deliverables already merged, and runs several times per deliverable. A task item runs its effect on the deliverable branch before its final review, gates and merge. An `E<n>:AC<k>` item runs again after every gates fix and late sync.
   3. **The `git show` sentence.** End the authorization message with one sentence, in the person's language, that names the exact command with the real values (`git show <target>:<reportPath>`). When `reportPath` is null, leave that sentence out.
   4. **On a yes.** Resume per step 4 with the union of the `resumeWith` of the actions the yes covers (only the named items on a partial yes): the `authorizeExternal` and `deliverables` of the resume are the union of the `resumeWith` of the authorized `authorize-external` actions, never taken from a summary. Details: operator.md item 3.
   5. **Source of the resume.** While the Workflow result is still in this conversation it is the source and the report (the operator actions section, in the roadmap's language) only a check: if they diverge, resume with the result and report the divergence. After a compaction the report is the source. Never answer from memory.
   6. **No source.** With no source (the report unavailable although `reportPath` was not null, or `reportPath` null and the result out of context), resume with the short items the person approved by name (`E<n>:T<m>`, `E<n>:AC<k>`, `gate:<id>`, `checkout:<target>`), which bind to the current plan on first use. If the names are lost too, resume without new items. Details: operator.md item 3.
   7. **Open launch.** For a `human-input` about an open launch (it asks for an empty commit `E<n> T<m>: external effect completed` or `E<n> T<m> awaiting person: confirmed not run`), write that empty commit only when the person states the outcome in their own message; never infer it.
