# § 3. Integration

**When:** a branch with roadmap work is merged into the configured `integrationBranch`. With `releaseBranch` set, a merge into that branch is § 15 instead, and the later merge of the release branch into `integrationBranch` is § 16. Decide first, once: `releaseBranch` set or a caller-supplied target (below) → § 15, else this recipe; § 15 never sends the event back here.

Caller-supplied target: when `releaseBranch` is unset and the caller names the branch the work merged into (for example the target of `roadmap-release`), apply § 15 with that branch: on-branch word, merge SHA in Evidence, the branch named in Next step. Never infer the target from the checked-out branch.

1. Get the SHA that entered the integration branch (the merge commit, or the merged tip for a fast-forward or squash result); ask for it if git cannot show it. Check it: `node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" verify-commit "<folder>" <sha> --json` → `exists` and `integrated` both true (the CLI accepts the local `integrationBranch` or `origin/<integrationBranch>`, so a stale local branch is fine). `integrated` false → do not mark integrated; tell the user. `exists` null (no git repository) → say the SHA was not verified and do not mark integrated.
2. Mark it: `node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" integrate "<folder>" --sha <sha> [--only E<a>,E<b>]`. It moves to the integrated word (position 6 of `deliverableStatuses`) every row whose segments are all on-branch with SHAs that are ancestors of the integration ref, adds the SHA to Evidence and writes its own log row (do not add one). Exit 0 with `integrated: []` means no row qualified (no-op): say so. Without git it refuses (DEC-201: integrated or later is never set unverified): report it. `sha-missing` and `sha-not-integrated` are exit 1: report them. A piece the command skips (a row with other pieces still on a branch) → `set-status "<folder>" E<n> <integrated word> --piece <label> --evidence <sha>`, then `log "<folder>" --deliverable E<n> --what "E<n> piece <k> integrated into <branch>" --evidence <sha>`. Never set a released status here: that goes through § 12, which also records the package. The checker needs at least one Evidence SHA that is an ancestor of the integration ref when the row has an integrated segment (`formats.md § 4`).
3. "In flight": the branch stays `vocab.branchLive` while it exists; once it is deleted, § 4 (`inflight-remove`). A log SHA that no longer exists (a deleted or squashed branch) is only a `sha-missing` warning, so old log rows stay as written.
4. Refresh `critical-path.md` (next milestone per track) by hand (volatile values: `formats.md § 4`), then § 2 step 4 (end of piece or phase? phase exit criteria first).

Checker: `not-integrated`, `sha-missing`, `integrated-no-sha`; `shallow-clone` or `integration-branch-missing` warnings mean the ancestry was not verified: say so in the report. The `no-git` warning (a SHA accepted without a check at positions 1 to 5) is reported the same way.
