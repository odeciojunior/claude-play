# § 17. Acceptance pending

**When:** the code of a deliverable is ready but the acceptance (usually human, for example a client sign-off or a smoke test in an environment nobody has yet) is not done.

1. Panel row as segments (words from `vocab`; segment rules in `formats.md § 4`). Two commands, each `node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" set-status "<folder>" E<n> <word> --piece <label> ...`: the `code` segment (`on-branch`, `--evidence <code SHA>`, `--next "<who must accept and what the evidence will be>"`) and an `acceptance` segment (`executing`, the status `block-close` will restore). Evidence cites the code SHA and the gate (volatile values in Evidence or Next step: `formats.md § 4`). `set-status` writes no log row. **Unsegmented row** (the usual case: Status is one word such as `executing`): `set-status --piece` refuses it with `segment-required` and the CLI has no command that splits a row into segments. Edit the Status cell of the panel row by hand to `code: on-branch; acceptance: executing` (the segment words keep the `vocab` spelling), put the code SHA and the gate in Evidence and the acceptance owner in Next step, then go to step 2; without the `acceptance` segment `block-open --piece acceptance` fails with `not-found`. Use `set-status --piece` only on a row that already carries segments.
2. Open the blocker: `node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" block-open "<folder>" --what "<acceptance awaited>" --affects E<n> --piece acceptance --unblocks "<condition>"`. It blocks only the `acceptance` segment, so the row reads `code: on-branch; acceptance: blocked (BLQ-n)`, and writes its own log row (do not add one). Refusals are exit 1: report them.
3. Human acceptance is never recorded as done without evidence: a sign-off message, a path to the signed record, or a command output the user supplies. No evidence → the acceptance segment stays blocked.
4. When the evidence arrives: `block-close "<folder>" BLQ-n --how "<how>" --evidence <ref>` (restores the `acceptance` segment, removes the row, writes its own log row), then `set-status ... --piece acceptance` to the status the evidence supports, then `log "<folder>" --deliverable E<n> --what "E<n> acceptance recorded" --evidence <ref>`. If the card's acceptance items carry `{verify: ...}` tags, the item's tag and evidence must match what was shown (`ac-verify-invalid` / `ac-verify-missing` are the warnings to watch).
