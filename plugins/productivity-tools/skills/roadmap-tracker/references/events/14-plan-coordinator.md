# § 14. Events from plan-coordinator

`plan-coordinator` invokes this skill with the event "wave N closed (steps …)" after each wave gate, and "plan completed" at the end, when its progress file header reads `**Roadmap**: <folder>`.

1. Read that progress file (the one the caller names; otherwise the `docs/plans/**/progress-*.md` whose `**Roadmap**:` field names this folder): the header (`**Plan**`), the Execution Map table (Wave, Group, Steps), the Steps table, the Wave Execution Log and any recorded commit SHAs. Never edit it.
2. Find the deliverable: the panel row whose Evidence or Next step cites that plan (or its spec); else the `E<n>` the plan's title or header names; else ask once. When the event says `no questions`, never ask: write each unanswered question as a `pending` item (`node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" add-pending "<folder>" --owner user --text "<question>"`) and list them under `Pending for the user:` in the Step 7 hand-back.
3. Decide which pieces closed: a piece closes when every plan step that implements it has Status PASS (or an intentional skip; a `Stopped` step with `Refused:` is not one; `Skip (manual)` and `Waiting (manual)` are work that did not run and never count). Throughout this item, a step whose Note says `replaced by Step Nr` is judged by Step Nr's status, not its own, following a chain of replacements to the last step. Map steps to pieces from the plan's own text (a step naming the piece, or a plan that covers exactly one piece); a replacement step belongs to the pieces of the step it replaced, even though the plan's text does not name it. When the progress file cannot tell which piece a step belongs to (an unmapped step): on "wave N closed" add one `log` row (`node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" log "<folder>" --deliverable E<n> --what "wave N closed (steps …)" --evidence <progress file>`) and set (`set-status`) from the artifacts that exist, per segment and only for a piece whose current status is earlier than that word (never lower a status or collapse segments into one): a plan file → the configured word for plan (position 3), only a spec file → the word for spec (position 2), else leave the status unchanged; on "plan completed" mark the pieces the plan covers with the word for on-branch (position 5), except when a step is `Skip (manual)`, `Waiting (manual)` or `Stopped` with `Refused:`: those states do not close a piece, so set from the artifacts as on "wave N closed". Never infer the integrated word (position 6) without a SHA that is on the integration branch.
4. Record per § 2 (`set-status`, then `log`). Evidence = the progress file path in backticks plus the commit SHAs it records (each verified with `git cat-file -e <sha>^{commit}`). Read the current branch with `git branch --show-current` and keep its "in flight" row `live` (`node "${CLAUDE_SKILL_DIR}/scripts/roadmap.mjs" inflight-add "<folder>" <branch>`; a no-op when already live).
5. Ask the user only for what the progress file cannot tell, such as an integration SHA (a plan that completed on a branch is `on-branch`, not integrated) or an ambiguous step-to-piece mapping. When the event says `no questions`, never ask: write each unanswered question as a `pending` item (`add-pending --owner user --text "<question>"`, as in step 2) and list them under `Pending for the user:` in the Step 7 hand-back.
6. If a piece or the deliverable closed, run the end-of-piece check (§ 9). Hand back to plan-coordinator with the Step 7 report; it continues with the next wave.
